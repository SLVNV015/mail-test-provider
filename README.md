## Как запустить

```bash
git clone git@github.com:SLVNV015/mail-test-provider.git
cd mail-test-provider
cp .env.example .env
```

Для запуска БД провайдера и воркера:
```bash
docker compose up -d 
```
Логи воркера. Должно вернуть 0 в случае успеха

```bash
docker compose logs -f worker
```
Для экспорта дождаться завершения работы воркера. Он не запустится сам его надо запускать ручками. Запуск экспорта:

```bash
docker compose run --rm exporter
```
Прибраться за собой:

```bash
docker compose down -v
```

## Как устроено хранение и почему

- `messages` — основная сущность, первичный ключ `external_id`
- `message_references` — список `References` с порядком, отдельно от сообщений
- `traversal_state` — cursor и флаг завершения для постраничной загрузки
- `parent_id` и `thread_key` хранятся в `messages` как вычисляемые поля

Выбрано так, чтобы не хранить массивы в строках и иметь возможность продолжать загрузку после остановки. Что бы вычислясть несуществующие рефы и reply_to joinами.

## Если появится второй почтовый сервис

Добавлю отдельный traversal adapter, который преобразует его формат во внутреннюю модель. Поскольку источник отдаёт готовые разговоры, adapter сразу формирует связи. Без изменений останутся: хранение, построение графа, экспорт.

## Что произойдёт при одновременном запуске двух сервисов

Проблема в `traversal_state`: оба процесса могут получить один cursor и обработать одну страницу. В `messages` дублей не будет благодаря `ON CONFLICT DO NOTHING`, но координация checkpoint нарушится. 

## Есть ли шаг, который нельзя выполнить дважды

Нет. Вычисление `parent_id` и `thread_key` идемпотентно, ingestion защищён `ON CONFLICT DO NOTHING`, cursor обновляется транзакционно.

## Что перестанет работать при 10x объёме

Первым упрётся память Node.js при построении DSU — граф целиком в памяти. При 125к записей DSU это около 20MB в памяти, но дальше больше. БД уже использует батчи и keyset pagination. Дальше — компактные numeric IDs или вынос connected components в отдельный этап.
